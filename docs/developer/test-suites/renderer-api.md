# `renderer/api/tests`

Covers the Flask pipeline API, the render worker, the Gemini review client, and the host-timezone
helper. One source tree, two containers — `tubematic-api` runs Flask plus the MCP server,
`tubematic-renderer` runs the worker from the same image with a different `command:`.

```bash
python -m pytest renderer/api/tests
```

> **Must run separately from `scripts/tests`.** Neither parent has an `__init__.py`, so pytest names
> both `tests/` directories the same top-level package and the second to be collected fails to
> import.

## What these encode

**The reviewer is told which visual register it is judging.** The prompt used to state no intended
style at all, so every video was judged against an unstated default — which for black line art on
white means `animation_defect` ("unclean, misplaced, or misaligned", wording written around
polished vector diagrams) and the prompt's open-ended escalation clause both fire on the register
itself. Under the "any finding routes to `REVISION_REQUESTED`" rule that is not a grading problem:
each round is a paid re-voice, so a systematically mis-judged register wedges the video. The tests
pin that the contract forbids the three specific false positives observed (flat art as low quality,
a held pose as broken animation, a white frame as a blank frame), that it still demands a real
review of legibility, safe zones and sync, and that an **unknown** register states no contract at
all — guessing is the one unsafe direction, because a wrong contract licenses defects the video has
no permission to contain.

**The captions' negative control matters more than the positive one.** Every video is now
captioned, so a reviewer that read the captions as text duplicating the narration would return a
finding on *every* video — and any finding routes to `REVISION_REQUESTED`. That is a wedged
pipeline, not a missed check, which is why the prompt states outright that the captions are correct
by design and why a test pins that sentence. The positive half — a scene that *also* writes out the
narration — is deliberately a suggestion rather than a must-fix, and a third test pins the carve-out
for text carrying its own information (a number, a pinned label, a chart axis), without which every
diagram beat would cost a revision round.

**The register's two figure clauses are pinned apart.** They began as one block sent whenever a
video could contain figures at all, which told an illustrated video — generated character artwork,
line art excluded — that simple line-art stick figures were intended. The tests pin that an
illustrated video loses the line-art clause and **keeps** the discrete-motion one, because the
error directions are not symmetric: over-sending the line-art clause costs a missed catch, while
dropping the held-pose licence costs false positives on every video in that register, and any
finding is a revision round. A further test pins that `line_art` without `figures` emits nothing,
so a stray flag cannot describe figures the video cannot contain.

**AI review fails open, deliberately.** A broken review advances the video to `VIDEO_READY` rather
than failing the pipeline. That went unnoticed for the feature's entire lifetime once already, which
is why the worker now writes a comment and `videos.gemini_feedback` on **every** outcome — pass,
defects, or error. The tests pin both the fail-open transition and the always-comment behaviour; they
are a pair, and removing the second makes the first invisible again.

**The review at the loop cap still runs.** The boundary is `count > cap`, not `>=`. With `>=` the
very first review at `cap = 1` would force acceptance, giving zero revision rounds ever. Tests pin
the strict comparison, and pin that the early-return shortcut is not reintroduced — it used to ship
renders carrying the *previous* round's stale feedback.

**Two separate loop caps.** `max_render_retries` governs render crash/timeout retries;
`ai_review_max_loops` governs the review loop. They used to be one key, so granting a review loop of
1 silently halved the render-retry budget. `test_worker.py` keeps them independent.

**`test_ai_review.py` exists because the older tests mocked too high.** The AI-review tests inside
`test_pipeline.py` mock `httpx.Client` wholesale, so an incorrectly shaped request body still passes.
`test_ai_review.py` asserts at the wire level instead — it is the file that would have caught the
upload bug that leaked an API key.

**Secrets are masked at the route boundary only.** `_read_all_settings` returns raw values because
internal callers need them; `GET /settings` **and the `POST` response** both mask. Masking only the
GET would leak a key on every save. Tests cover both directions.

**An HTTP client's own request log is a leak path when the credential is in the URL.** Every other
provider here sends its key as a header, so the client's `HTTP Request: <method> <url>` line is
harmless; a Discord webhook token is in the path, so that line prints a live credential on every
call. Found by running the feature against a real stack, not by reading the code — a working token
reached both `docker logs` and a JSONL file. Two tests pin the fix, and one pins that it did not
become a blanket suppression of the client's logging, which is how the other providers get debugged.

**The webhook URL is a credential, and the tests treat it as one.** Anyone holding it can post to
that channel. HTTP clients put the request URL in their exception text and this pipeline persists
exception text into the dashboard-visible `comments` table, which is how a key leaked once.
`test_discord_notify.py` asserts the token is absent from every error the module can produce,
including a transport failure and an HTTP error whose body echoes the request.

**Only a positive rejection may gate a settings save.** The webhook probe is tri-state: a `401` or
`404` refuses the save, but a timeout, a `5xx` or a rate limit stores the URL anyway. Tests pin
both halves — collapsing "unreachable" into "invalid" would make Settings un-saveable whenever
Discord is unwell.

**Composition clips rather than hoping.** Discord answers `400` when an embed exceeds any size cap,
and a rejected message is a notification nobody ever receives, with nothing reporting the loss. The
tests run every builder against deliberately absurd input and assert every documented limit,
including the 6000-character total across a message.

**Five sweep behaviours are load-bearing**, each of them a real bug if it regressed: the migration
backfill (so an upgrade does not announce months of parked videos at once), backlog suppression
while a trigger is off (so switching one on does not fire everything parked since), second arrivals
(so a video returning to a checkpoint after a revision round is announced again), leaving
`updated_at` untouched (it is the FIFO ordering key for the render claim, so notifying must not
reorder the render queue), and not advancing the marker on a failed send (so the next tick retries
instead of losing it).

**The second-arrival test deliberately runs the whole round with no sweep in between.** An earlier
cut keyed the marker on the status name alone and passed a test that swept at each step, while
silently dropping the second notification in the case that actually happens — a revision requested
and acted on while the worker is inside a render. The no-sweep version is the one that pins the
behaviour; keep it.

**A publish that is still uploading must never be failed.** Flask writes the publication rows at the
claim, with an empty post id, and the worker treats such rows as in flight. The regression test drives
the real publish route and runs a real worker pass from *inside* the upload, the exact moment the
original bug struck: postforme has no post yet, and the old worker read that as a crashed publish and
failed a video that went live seconds later. It fails against the old code and must keep doing so.
The same section pins that a dead post under the video's id is not adopted before the deadline,
since it can belong to an earlier attempt. It also pins that adopting a post restarts the deadline,
and that expiry never fails a video whose post id was filled in at the same moment.

**A publish request must always end before the worker's deadline.** Past it, a late `create_post`
would have nothing correct to attach to. `test_worker.py` asserts the arithmetic, which is the upload
cap plus the per-operation timeouts, against `_PUBLISH_TIMEOUT_SECS`, so raising one timeout
without the other fails a test instead of reopening the race. `test_pipeline.py` pins that a
request fills only the rows it inserted itself.

**Scheduling: the wall time is converted by the API, and a cancel must never strand a post.**
`resolve_schedule` is tested with a fixed `now`: a zone's offset is taken on the scheduled day, not
today, so a New York time in December is UTC-5 even when the test runs in summer; a wall time the
clocks skip is refused rather than silently shifted, which is what `zoneinfo` would otherwise do; a
repeated hour takes its first occurrence, or the second once the first is too soon — "in one hour"
during the first occurrence is the same wall time again, and was refused as too soon until a review
caught it. Through the route, a bad schedule is a `400` that creates
nothing, a failed upload clears the schedule with the claim, and a post the upload leaves within a minute
of its time (`SCHEDULE_POST_NOW_SECS`, already passed or not) is sent as a publish-now, because postforme refuses a past `scheduled_at` and the route would have to
read that as ambiguous. The cancel tests pin the order — postforme first, local state after: a `400`
(already going out) and an ambiguous failure both leave the rows, a `404` releases only once postforme
no longer lists the post, and a cancel racing the worker's due-time move to `PUBLISHING` still
releases, since a deleted post cannot go out.

**Retry publishing never posts twice.** It asks postforme before acting, adopts a live post rather
than re-posting, treats a post that failed everywhere as not posted, and treats a postforme outage
as "unknown", never as "nothing was posted". The claim on `FAILED` is atomic, and a test forces two
overlapping retries to show that only one acts.

**The version is asserted against `tubematic_core.version.version()`, never a literal.** Otherwise
the test would need editing on every release, and — more usefully — it would stop failing if a
second definition of the version were ever introduced and drifted from the real one. A sibling test
pins that `/stats` is still a pure status→count map, which is the reason the version was put on
`/pipeline/status` instead: callers iterate `/stats` expecting every value to be a count.

**`hosttz` reads glibc's cached zone.** `timezone_label` comes from `datetime.now().astimezone()`,
which does not see a `/etc/localtime` change made after the process started. The test documents the
caching behaviour rather than asserting a specific zone.
